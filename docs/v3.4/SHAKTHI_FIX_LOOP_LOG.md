- Problem: Founder found live that anyone could get Resume AI's paid prompts without paying. Separately asked to "re-review payment terms as per services" after the pricing redesign.
- Root cause: `app/resume-ai/page.tsx` rendered the fully-built prompt in a `<pre>` block unconditionally (`hasAccess` only gated the Copy button's clipboard call, not what was displayed), and since the page was a `"use client"` component, the entire `buildPrompt()` template logic shipped in plain JS to every visitor's browser regardless of payment — there was no server-side secret at all, just a UI gate on already-public content. Separately, `app/terms/page.tsx`/`app/refunds/page.tsx` still hard-coded the old flat ₹99 single-SKU pricing contractually, left stale by the earlier pricing-redesign commit.
- Fix: moved the real prompt templates into a new server-only module `lib/resumePrompts.ts` (never imported by any client component); added `app/api/resume-ai/prompt/route.ts`, a POST route that checks real access (owner email or a `payments` row with `status: "paid"` on an access-granting plan id) before returning the real prompt, and returns a generic 403 otherwise — never any real template text. `app/resume-ai/page.tsx` now shows a generic locked placeholder until a real fetch succeeds, and copies only the server-fetched text. Rewrote `terms`/`refunds` to describe the real current one-time tiers (Free / SmartBudget Pro ₹149 / All Access ₹399), state PDF Studio/PeopleDesk are free and ungated, and describe LeakShield/Resume AI's actual (non-guaranteed) behavior honestly.
- Files changed: `lib/resumePrompts.ts` (new), `app/api/resume-ai/prompt/route.ts` (new), `app/resume-ai/page.tsx`, `app/terms/page.tsx`, `app/refunds/page.tsx`.
- Test/build result: `npm run build` pass, `npm run lint` pass (fixed one `react-hooks/set-state-in-effect` violation by moving loading/error state resets into the debounced async fetch callback instead of the synchronous effect body), `npm test` pass 5/5. - Prevention rule: any page that renders paid/proprietary generated content must fetch that content from a server route that checks access itself — a client-side `hasAccess` boolean can gate a button, but never the content sitting next to it, and a `"use client"` file always ships its full source to every visitor regardless of any runtime check inside it.

- Task: Task 1 — DhanSetu AI Budget Tracker + LeakShield
- Problem: LeakShield™ was marketed on the dhansetuhub.in homepage (feature grid, FAQ, a static illustrative "leakCard" example) but the nav explicitly marked it "🔒 LeakShield™ ROADMAP" — no real detection logic existed anywhere in the codebase. The live SmartBudget demo copy even said outright: "The live product supports transaction CRUD, category budgets and monthly reports" (no leak detection).
- Root cause: the feature was scoped and named in marketing copy ahead of the underlying engineering work being scheduled.
- Fix: implemented real analysis in `lib/leakshield.ts` (pure functions, no fabricated numbers) covering four signals — category overspending vs budget, recurring-charge/subscription clustering (same category, amount within 5%, recurring across ≥2 distinct months), low-savings-rate warning (<15% of income retained), and cash-flow risk (expenses rising 3 consecutive months while income is flat/down). Wired into a new `app/api/leakshield/route.ts` (auth-gated via the existing `getUser()`/D1 pattern) and a new "LeakShield" tab in `app/smartbudget/smartbudget-app.tsx`, with an honest "not enough history yet" empty state when a user has fewer than 5 transactions. Homepage nav marker changed from locked/"ROADMAP" to "LIVE".
- Files changed: `lib/leakshield.ts` (new), `app/api/leakshield/route.ts` (new), `app/smartbudget/smartbudget-app.tsx`, `app/page.tsx` — all on branch `task1-leakshield` (commit `7132986`), cut from `origin/main`, not merged into local `main`, not pushed.
- Test/build result: `npm run build` pass, `npm run lint` pass (0 errors), `npm test` pass (5/5 existing tests green, none broken by this change). LeakShield math independently sanity-checked with a synthetic 10-transaction/3-month dataset via `npx tsx` — all four signal types fired correctly on the expected inputs and stayed silent on the "no leak" categories.
- Prevention rule: don't let homepage/marketing copy describe a feature as live before its detection logic exists — a locked "ROADMAP" marker (as this one correctly was) is the honest state until the real code lands; flip it only in the same change that ships the logic.
